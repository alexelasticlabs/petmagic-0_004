# Mobile build automation

## Goal

PetMagic uses the company Mac mini as the dedicated mobile build machine. GitHub
keeps source control, protected environment secrets and workflow logs, while the
Mac executes Android and iOS jobs as a repository-scoped self-hosted runner.
This avoids paid GitHub-hosted macOS minutes and keeps release tooling in one
maintained macOS environment.

This document describes the intended configuration. It is **not evidence that
the runner has been installed or that a Store build has passed**. Record those
facts in `docs/release-readiness.md` only after live verification.

## Workflow profiles

| Profile | Purpose | Store upload |
| --- | --- | --- |
| `mobile-fast-check` | Formatting, localization validation, static analysis and stable Flutter tests. No APK, AAB, IPA, emulator or simulator. | Never |
| `mobile-ci-full` | Explicit regression suite: release-smoke and optional device scenarios. | Never |
| `mobile-release` with `publish=false` | One signed release-candidate build for the selected platform. | Never |
| `mobile-release` with `publish=true` | Deliberate Play Internal or TestFlight release. The protected environment remains required. | Yes |
| `mobile-promote` | Deliberate promotion of an already uploaded Store build. | Yes |

Normal code work uses `mobile-fast-check`. Device suites and release-candidate
builds are opt-in. A Store upload must be an explicit human decision, not a
side effect of a smoke build.

## Visual golden baselines

`mobile-fast-check` excludes only tests tagged `platform-golden`. These are
pixel baselines whose checked-in reference images were produced on a different
host rendering stack and currently differ by up to 17% on macOS ARM despite
the deterministic font harness. They are not removed: the remaining widget
and golden tests still run in every fast check, while these exact visual
baselines must be reviewed on their canonical rendering host before accepting
an image update. Run them deliberately with:

```bash
cd apps/petmagic-mobile
flutter test --concurrency=1 --tags=platform-golden
```

Never use `--update-goldens` merely to make the Mac runner green. A changed
reference image must be reviewed as a UI change.

## Mac mini runner boundary

- Register the runner **only for this repository**, not for the account or an
  organization.
- Use the additional label `petmagic-mobile`. Workflows target
  `[self-hosted, macOS, petmagic-mobile]` and cannot run on an arbitrary
  company runner.
- Install the runner as a macOS service. Its work directory must be separate
  from personal and production checkouts.
- Allow workflows only from trusted repository refs. Do not add forked-pull-
  request triggers to workflows that can receive protected release secrets.
- The runner's persistent directories may cache public dependencies (Flutter,
  Gradle, CocoaPods and Bundler). Never place keys, `.env` files, Firebase
  active configuration, signing archives or database data in those caches.
- Release workflows remove copied Android/iOS credential files at the end of
  each job. The source-of-truth secrets remain GitHub protected-environment
  secrets or the dedicated Match repository.

## First-time preflight

On the Mac mini, from a clean PetMagic checkout:

```bash
bash scripts/ci/bootstrap-macos-runner.sh
```

The script makes no external changes. It checks for the pinned Flutter version,
Xcode, Ruby/Bundler, Java and required command-line tools, and creates only
private dependency-cache/log directories under `~/.cache/petmagic-ci`.

After the preflight passes, create the runner in GitHub:

1. Open **Repository → Settings → Actions → Runners → New self-hosted runner → macOS**.
2. Run the commands generated by GitHub **on the Mac mini**. The registration
   token is short-lived; do not send it in chat or save it in a file.
3. Add the label `petmagic-mobile` when configuring the runner.
4. Use the generated `./svc.sh install` and `./svc.sh start` commands so it
   survives a logout/restart.
5. Confirm the runner appears as `Idle` in GitHub before enabling a workflow.

## Operating rules

- Do not use `platform=all` merely to check a UI change.
- Use `publish=false` for QA or a locally installed release candidate.
- Use `publish=true` only after the target Store, version and environment have
  been explicitly reviewed.
- Keep release artifacts in GitHub only when a reviewer actually needs them;
  their retention is seven days. Store uploads and crash-symbol processing do
  not require an Actions artifact backup.
- A self-hosted runner eliminates GitHub runner minutes, not the operational
  need to update macOS/Xcode/Flutter, protect the Mac account and monitor free
  disk space.
- `ruby/setup-ruby` uses non-relocatable macOS binaries. If it tries to write
  `/Users/runner/hostedtoolcache`, run the manual `runner-maintenance` workflow
  with its acknowledgement. It prepares only that standard tool-cache path and
  refuses to alter an existing directory owned by another macOS user. The
  runner account must have passwordless `sudo`; otherwise run the same script
  from a Mac administrator session. No runner restart is required afterwards.
